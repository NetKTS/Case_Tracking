## 1. ทำไมถึงสร้าง web นี้

### ผู้เกี่ยวข้อง
- **A** — บริษัทผู้พัฒนาโปรแกรม (ทีม Support/CX, Product, Dev, Tester, Publish)
- **C** — ลูกค้าผู้ใช้โปรแกรม มีหลายบริษัท (C_1, C_2, C_3 …) แต่ละบริษัทมี web ของตัวเอง **1 domain** และแต่ละ domain ใช้โปรแกรมของ A **คนละเวอร์ชัน**

### ปัญหา (จาก Design Thinking)
ลูกค้าแจ้งบัคเข้ามาแล้ว **ไม่รู้เลยว่าปัญหาได้รับการแก้ไขหรือยัง แก้ถึงไหนแล้ว** บางเคสเงียบหายเป็นเดือน ทำให้ลูกค้าต้องโทรตาม ไม่มั่นใจ และไปบ่นต่อกับผู้บริหาร ขณะที่ฝั่ง A เองก็ไม่มีภาพรวมว่าเคสไหนค้างอยู่ที่ใคร เจ้าไหนแจ้งเยอะ หรือเวอร์ชันไหนมีปัญหา

### Flow การทำงานจริงของ A
1. ลูกค้าแจ้งปัญหาเข้ามาที่ **Support (CX)**
2. Support ตรวจสอบ ถ้าแก้ได้ → แก้ให้ลูกค้าทันที
3. ถ้าไม่แน่ใจหรือน่าจะเป็นบัค → ส่งให้ **Product** ตรวจว่าเป็น Bug จริง หรือเป็นการทำงานตาม Spec
4. ถ้าเป็น Bug → ส่ง **Dev** แก้ไข
5. **Tester** ทดสอบ — ไม่ผ่านส่งกลับ Dev, ผ่านแล้ว **Tester Publish เอง** ให้ domain ของลูกค้า (แต่ละบริษัทแยกกัน)
6. **ลูกค้า** ตรวจสอบและกดยืนยันปิดเคสเอง พร้อมให้คะแนน

## 2. ระบบช่วยเรื่องอะไรได้บ้าง

| Idea จากทีม | ระบบช่วยอย่างไร |
|---|---|
| **#1** ติดตามการ์ดได้เหมือนติดตามพัสดุ | ทุกเคสมีเลข (CS-xxxx) และแถบความคืบหน้า 6 ขั้น — บอกว่า "ตอนนี้อยู่ที่ใคร" และ "ขั้นตอนถัดไป" พร้อมประวัติทุกการเปลี่ยนแปลง |
| **#2** Dashboard สรุปการ์ดที่แจ้งมา / ที่ยังค้าง | หน้า Dashboard (หน้าแรก) — ลูกค้าเห็นสรุปของบริษัทตัวเอง, ทีมงานเห็นทุกบริษัท: เจ้าไหนแจ้งเยอะ, ค้างที่ไหน, เวอร์ชันไหนมีปัญหา, ความพึงพอใจ |
| **#3** แจ้งประมาณการเสร็จ ลดความคาดหวังลอยๆ | ยืนยัน Bug ต้องระบุ ETA, ส่ง Publish ต้องระบุวันที่และเวอร์ชัน, เลื่อนวันต้องบอกเหตุผลให้ลูกค้าเห็น, เลยกำหนดขึ้นป้ายเตือน |
| **#4** ใครกันที่คุยกับฉันอยู่ ไม่อยากคุยกับโรบอท | ลูกค้าเห็นชื่อผู้ประสานงาน Support คนเดิมตลอดเคส + ช่องทางติดต่อ, ทุกข้อความแสดงชื่อคนและทีม, ต้องกด "รับเคส" เพื่อระบุผู้รับผิดชอบ |
| **#5** เคสนิ่งเกินวันต้องเตือนทีม | กฎยกระดับ 2 ระดับ (ดูข้อ 4), 🔔 กระดิ่งแจ้งเตือน, CX กด "ทวงถาม" ทีมอื่นได้, ลูกค้ากด "สอบถามความคืบหน้า" ได้ตลอด |
| **#6** ระบบล่ม มีประกาศแจ้งไว้ก่อน ลดการปะทะ | Admin สร้างประกาศ → แถบประกาศขึ้นทุกหน้า (รวมหน้า Login), ตอนลูกค้าจะแจ้งเคสใหม่ระบบเตือนว่า "ทีมทราบแล้ว ไม่ต้องแจ้งเพิ่ม" |
| **#7** สรุปเคสรายสัปดาห์ระดับบริษัท ส่งผู้บริหาร | หน้าสรุปรายสัปดาห์ — อีเมลสรุปต่อบริษัททุกวันจันทร์ 09:00: แจ้งใหม่, ปิดแล้ว, ยังค้างที่ไหน, กำหนดการ, เคสที่รอลูกค้า, ความพึงพอใจ |
| **#8** เคสจบที่ลูกค้า + ประเมิน + แจ้งว่าต้อง Publish | เคสไม่ปิดเมื่อทีมทดสอบผ่าน แต่รอลูกค้ากดยืนยันพร้อมให้ดาว 1–5, มีสถานะ "รอ Publish" บอกว่าจะได้เวอร์ชันไหน วันไหน |

> **ข้อจำกัดของ demo:** ข้อมูลเก็บใน browser ของแต่ละคน และการแจ้งเตือน / อีเมลรายสัปดาห์ยังเป็นแบบในเว็บ / จำลอง — ระบบจริงต้องมี backend (ดู HANDOFF.md ข้อ 7)

## 3. สถานะของเคส

### ภาพรวม flow

```
ลูกค้าแจ้ง → 📥 แจ้งเข้ามาใหม่ → 🎧 Support ตรวจสอบ ─┬─ แก้ได้เลย ──────────────────────────────┐
                                                      └→ 🧭 Product ตรวจสอบ ─┬─ เป็นไปตาม Spec ────┤
                                                                            └→ 🐞 ยืนยัน Bug        │
                                                                               → 🛠️ Dev กำลังแก้ไข  │
                                                                               ⇄ 🔍 Tester ทดสอบ     │
                                                                               → 🚀 รอ Publish       │
                                                                                                     ↓
                                                        ✅ แก้ไขแล้ว · รอลูกค้ายืนยัน → 🔒 ปิดเคส
ระหว่างทาง Support / Product / Dev / Tester ขอข้อมูลเพิ่มได้ → ⏳ รอข้อมูลจากลูกค้า → ตอบแล้วกลับขั้นเดิม
```

### รายละเอียดแต่ละสถานะ

| สถานะ | ความหมาย | ลูกค้าเห็นว่า | เคสอยู่ที่ (ผู้รับผิดชอบ) | SLA |
|---|---|---|---|---|
| 📥 **แจ้งเข้ามาใหม่** | ลูกค้าแจ้งปัญหาเข้ามา รอ Support รับเรื่อง | รับเรื่องแล้ว | Support | 4 ชม. |
| 🎧 **Support ตรวจสอบ** | Support ตรวจสอบ / ทำซ้ำปัญหา ถ้าแก้ได้จะแก้ให้ทันที | กำลังตรวจสอบ | Support | 2 วัน |
| ⏳ **รอข้อมูลจากลูกค้า** | ต้องการข้อมูลเพิ่ม (ภาพหน้าจอ, ขั้นตอน) — SLA ของทีมหยุดนับ | รอข้อมูลจากคุณ | ลูกค้า | 3 วัน |
| 🧭 **Product ตรวจสอบ** | ตรวจกับ spec ว่าเป็น Bug จริง หรือเป็นการทำงานตามที่ออกแบบ | ผู้เชี่ยวชาญตรวจสอบ | Product | 3 วัน |
| 🐞 **ยืนยัน Bug · รอคิวแก้** | ยืนยันแล้วว่าเป็น Bug มีกำหนดแก้ไข (ETA) | ยืนยันปัญหา · รอคิวแก้ | Dev | 5 วัน |
| 🛠️ **Dev กำลังแก้ไข** | Dev แก้ไข Bug | กำลังแก้ไข | Dev | 5 วัน |
| 🔍 **Tester ทดสอบ** | Tester รับต่อจาก Dev ทดสอบผลการแก้ไข | กำลังทดสอบ | Tester | 2 วัน |
| 🚀 **รอ Publish** | ทดสอบผ่านแล้ว รอ Publish เวอร์ชันใหม่ให้ domain ของลูกค้า | รอ Publish เวอร์ชันใหม่ | Tester | 3 วัน |

### 🗂️ งานที่ค้างอยู่ที่คุณ (บน Dashboard)

Board บนสุดของหน้า Dashboard แสดงเคสที่ค้างอยู่ที่คนที่ login — สถานะปัจจุบันเสมอ (ไม่ขึ้นกับช่วงเวลา) เรียงเคสเร่งด่วนก่อน (ยกระดับ / เกิน SLA) คลิกการ์ดเพื่อเปิดเคส

| บทบาท | คอลัมน์ |
|---|---|
| 🎧 Support · 🧭 Product · 💻 Dev · 🧪 Tester | ✋ ยังไม่มีคนรับ (ในทีม) · 👤 มอบให้คุณ · 👥 คนอื่นในทีม (ติ๊กแสดงได้) |
| 👤 ลูกค้า | ⏳ รอข้อมูลจากคุณ · ✅ รอคุณยืนยันผล · 📂 ทีมกำลังดำเนินการ (ติ๊กแสดงได้) |
| 🛡️ Admin | 🚨 ยกระดับ 2 · ⚠️ ยกระดับ 1 · ✋ ยังไม่มีคนรับ |

- สลับการแสดงผลได้ **▦ การ์ด** (คอลัมน์) หรือ **☰ List** (ตาราง มีคอลัมน์ "กลุ่ม") — ระบบจำรูปแบบที่เลือกไว้
- การ์ด / แถวแสดงป้าย 🔔 ถูกทวงถาม, ยกระดับ, ยังไม่มีคนรับ, ETA / วัน Publish และ SLA
- **💬 ข้อความที่ยังไม่ได้อ่าน:** ป้ายสีแดงพร้อมจำนวน บนการ์ด / แถว และสรุปรวมที่หัว Board — นับความคิดเห็น, ข้อมูลที่ลูกค้าส่งกลับ, การสอบถาม / ทวงถาม จากคนอื่น (ไม่นับของตัวเอง, ลูกค้าไม่นับข้อความภายใน) · เปิดหน้าเคส = อ่านแล้ว ข้อความใหม่ในหน้าเคสมีป้าย "ใหม่"

### การแสดงชื่อผู้รับผิดชอบ

| ผู้ดู | "ตอนนี้อยู่ที่" / ผู้รับผิดชอบ | การ์ด "ทีม / คนที่ดูแลเคสนี้" |
|---|---|---|
| ทีมงาน (ทุก role ที่ไม่ใช่ลูกค้า) | **ชื่อคนที่รับเคส** (ยังไม่มีคนรับ → ชื่อทีม) | ชื่อคนของแต่ละทีม |
| ลูกค้า | **ทีม / บทบาท** ที่ดูแลการ์ดอยู่ เช่น 💻 ทีม Dev | สถานะของแต่ละทีม: ● กำลังดูแล / ✓ ดูแลแล้ว / — |

ลูกค้ายังเห็นชื่อ **ผู้ประสานงาน Support** ของตัวเอง (IDEA#4 — รู้ว่าคุยกับใคร)

## 4. กฎยกระดับเคสนิ่ง (กันการ์ดไม่มีคน take action)

| ระดับ | เกิดเมื่อ | แจ้งเตือนถึง |
|---|---|---|
| ⚠️ **ระดับ 1** | ยังไม่มีคนรับเคสเกิน 2 ชม. · ผู้ถือเคสไม่มีความเคลื่อนไหวเกิน 1 วัน · เกิน SLA | ทีมที่ถือเคส + CX (Support) |
| 🚨 **ระดับ 2** | ไม่มีความเคลื่อนไหวเกิน 2 วัน · เกิน SLA 2 เท่า | + หัวหน้าทีมที่ถือเคส + Admin |

- นับ "ความเคลื่อนไหว" เฉพาะจากผู้ถือเคส (เปลี่ยนสถานะ, รับเคส, ตอบข้อความ) — การทวงถามจากคนอื่นไม่นับ
- ปลดการยกระดับได้ด้วยการกด "รับเคส" หรือดำเนินการต่อ
- CX (Support) เห็นเคสยกระดับของทุกทีม เพราะเป็นผู้ประสานงานกับลูกค้า

## 5. สิ่งที่แต่ละ Role ทำได้

### 👤 ลูกค้า (C)
- Login โดยเลือกบริษัทของตัวเอง — **เห็นเฉพาะข้อมูลของบริษัทตัวเอง**
- **แจ้งปัญหาใหม่** — ระบบแนบ domain และเวอร์ชันโปรแกรมให้อัตโนมัติ
- **ติดตามเคส** — ความคืบหน้า 6 ขั้น, ตอนนี้อยู่ที่ทีมไหน/ใคร, ขั้นถัดไป, ETA / วัน Publish, ประวัติ (ไม่เห็นข้อความภายในของทีม)
- **ตอบกลับ** เมื่อถูกขอข้อมูลเพิ่ม, **สอบถามความคืบหน้า** และ **แสดงความคิดเห็น** ได้ไม่จำกัด
- **ยืนยันปิดเคส + ให้คะแนน 1–5 ดาว** หรือ **แจ้งว่ายังไม่หาย** (เคสกลับไป Support)
- **ยกเลิกเคส** ได้ตอนแจ้งใหม่ / Support ตรวจสอบ / รอข้อมูล
- ดู **Dashboard** และ **สรุปรายสัปดาห์** ของบริษัทตัวเอง, ตั้งรายชื่อผู้บริหารที่รับอีเมลสรุป
- เห็น **ประกาศเหตุขัดข้อง** ที่กระทบบริษัทตัวเอง

### 🎧 Support (CX)
- **รับเรื่อง** เคสใหม่, **แก้ไขให้ลูกค้าเอง** ถ้าทำได้
- **ส่งต่อ Product** เมื่อไม่แน่ใจหรือน่าจะเป็นบัค
- **ขอข้อมูลเพิ่ม** จากลูกค้า
- **ทวงถาม** ทีม Product / Dev / Tester / Publish เมื่อเคสนิ่ง — เป็นผู้ประสานงานหลักกับลูกค้าตลอดเคส
- **ปิดเคส** เมื่อลูกค้าไม่ตอบกลับ 7 วัน
- แจ้งเคสแทนลูกค้าได้ (เช่น ลูกค้าโทรมา) โดยเลือกบริษัทและช่องทาง
- เห็นเคสทุกบริษัท (Board / List), Dashboard ทุก domain, ได้รับแจ้งเตือนเคสยกระดับของทุกทีม
- ตั้งค่าสรุปรายสัปดาห์ (ผู้รับ, เปิด/ปิดส่งอัตโนมัติ)

### 🧭 Product
- ตรวจเคสที่ Support ส่งมา แล้วตัดสิน: **ยืนยันเป็น Bug** (ต้องใส่ ETA) · **เป็นไปตาม Spec** (อธิบายให้ลูกค้า) · **ส่งกลับ Support**
- **ขอข้อมูลเพิ่ม** จากลูกค้า, **ปรับ ETA** พร้อมเหตุผล
- รับเคส / แสดงความคิดเห็น / บันทึกภายใน

### 💻 Developer
- **เริ่มแก้ไข** เคสที่ยืนยัน Bug แล้ว → **แก้เสร็จส่ง Tester**
- **ขอข้อมูลเพิ่ม** จากลูกค้า, **ปรับ ETA** พร้อมเหตุผล
- รับเคส / แสดงความคิดเห็น / บันทึกภายใน

### 🧪 Tester
- **รับงานต่อจาก Dev** แล้วทดสอบ
- **ทดสอบไม่ผ่าน → ส่งกลับ Dev** (ระบุสิ่งที่ไม่ผ่าน)
- **ทดสอบผ่าน → กำหนดวัน Publish** (ระบุ version และวันที่จะ Publish)
- **ขอข้อมูลเพิ่ม** จากลูกค้า, **ปรับ ETA**
- **Publish เวอร์ชันใหม่ให้ domain ของลูกค้า** (แต่ละบริษัทแยกกัน) แล้วแจ้งลูกค้าให้ตรวจสอบ — เวอร์ชันของ domain นั้นอัปเดตอัตโนมัติ
- **ปรับวัน Publish** พร้อมเหตุผลที่ลูกค้าเห็น
- รับเคส / แสดงความคิดเห็น / บันทึกภายใน

### 🛡️ Admin
- **ทำได้ทุก action ในทุกสถานะ**
- **สร้าง / อัปเดต / ปิดประกาศเหตุขัดข้อง** เลือกได้ว่ากระทบทุกบริษัทหรือบางบริษัท
- เข้าหน้า **Admin Spec** (บันทึก spec และ flow ของแต่ละหน้าในเว็บ)
- ได้รับแจ้งเตือนเคสที่ยกระดับถึงระดับ 2
- (demo: login ด้วยชื่อ `admin`)

### ทุก role ที่เป็นทีมงาน
- เห็นเคสทุกบริษัท, Dashboard เปรียบเทียบทุก domain, หน้า Workflow & สิทธิ์
- 🔔 กระดิ่งแจ้งเตือนเรื่องที่รอตัวเอง (เคสยกระดับ, ยังไม่มีคนรับ, ถูกทวงถาม)

## 6. หน้าในระบบ

| หน้า | ใช้ทำอะไร | ใครเข้าได้ |
|---|---|---|
| Login | เข้าระบบ เลือกบทบาท (+ บริษัท) | ทุกคน |
| 📖 Spec | เอกสารนี้ในเว็บ — ที่มา, สถานะ, สิทธิ์แต่ละ role | ทุกคน (ไม่ต้อง login) |
| 📊 Dashboard | หน้าแรก — **🗂️ งานที่ค้างอยู่ที่คุณ** (Board ตามบทบาท) + ภาพรวมเคสรายบริษัท / domain / เวอร์ชัน | ทุก role |
| Case Tracking | รายการเคส (Board / List / การ์ดของลูกค้า), แจ้งปัญหาใหม่ | ทุก role |
| รายละเอียดเคส | ความคืบหน้า, ปุ่ม action ตามสิทธิ์, ประวัติ, ผู้ติดต่อ | ทุก role |
| 📨 สรุปรายสัปดาห์ | ตัวอย่างอีเมลสรุปถึงผู้บริหาร, ผู้รับ, ประวัติการส่ง | ทุก role |
| Workflow & สิทธิ์ | แผนภาพ flow, ตารางสถานะ, ตารางสิทธิ์, กฎยกระดับ | ทุก role |
| 📢 ประกาศ | จัดการประกาศเหตุขัดข้อง | Admin |
| Admin Spec | บันทึก spec และ flow ของทุกหน้า | Admin |
